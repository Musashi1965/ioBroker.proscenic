# Technical Architecture

Status: initial boundary definition; public objects and concrete APIs remain
subject to PoC evidence.

## Core rule

ioBroker is the platform boundary. The public object tree is a versioned
projection of normalized device behavior, not a dump of undocumented cloud or
gateway payloads.

## Layers

```text
ioBroker lifecycle / config / objects / messages
                         |
application services: device registry, status, commands
                         |
domain contracts: identity, capability, snapshot, errors
                    /                       \
legacy REST client                    gateway socket client
login / devices / commands      discovery / framing / crypto / events
                    \                       /
                   Proscenic cloud and robot
```

Dependencies point inward toward project-owned domain contracts. Protocol code
must not write ioBroker states directly, and state handlers must not call raw
HTTP or socket functions directly.

## Planned modules

- `adapter`: lifecycle, configuration, subscriptions, object reconciliation,
  unload, and messages.
- `domain`: normalized identity, capabilities, status, commands, and errors.
- `backends/proscenic`: facade coordinating REST and gateway clients, session
  renewal, reconnect, and event normalization.
- `protocol/rest`: bounded HTTPS requests for login, devices, gateway discovery,
  and commands.
- `protocol/gateway`: TCP framing, authentication, decryption, validation,
  heartbeat/reconnect, and cleanup.
- `objects`: versioned ioBroker definitions and idempotent projection.
- `security`: redaction and credential/session boundaries.
- `maps`: optional bounded decoding/rendering isolated from core status; not
  part of the first milestone.

## Lifecycle

```text
stopped -> authenticating -> discoveringDevice -> discoveringGateway
       -> connecting -> online -> recovering -> online
                         \-> unavailable
```

User-initiated unload is distinct from unexpected disconnect and must never
schedule recovery. Authentication failure, cloud unavailability, gateway
failure, malformed frames, decryption failure, and robot offline state remain
separate stable error categories.

## Event and command flow

```text
gateway event -> validate/decrypt -> normalize -> project with ack=true
```

```text
ioBroker write ack=false -> validate -> capability check -> serialize command
  -> REST execution -> confirmation/result -> states with ack=true
```

No optimistic success may be reported as confirmed device state. If the
protocol provides no confirmation, expose an explicit command result and keep
that limitation documented.

## Identity

The vendor serial is required by the protocol but is installation-specific. It
must not be logged or used verbatim as a publicly documented example. Before
the object contract is frozen, the project must decide whether object IDs use a
stable derived identifier or an encrypted/persisted mapping. Display name and
network address are never identity.

## Credentials and sessions

Admin credentials use ioBroker `protectedNative` and `encryptedNative`. The
runtime token remains memory-only, is redacted from all errors, and is renewed
through a bounded authentication path. See ADR 0004.

## Testing boundaries

- REST and gateway clients use synthetic responses and frames generated by the
  project; private captures are not test fixtures.
- Domain, normalization, retry, redaction, object projection, and command
  semantics are unit tested without network access.
- Adapter integration tests cover startup, objects, state flow, restart,
  unload, and compact mode.
- Real-device tests are private, redacted, and recorded only as a compatibility
  result matrix.
- Cloud tests are never part of public CI because they would require live
  credentials and an undocumented external service.

## Open decisions

- stable public device identifier and first object contract;
- exact runtime and js-controller baseline after skeleton generation;
- gateway heartbeat and reconnect policy after the read-only PoC;
- command confirmation semantics;
- map storage, serving, size limits, and privacy policy;
- multi-device/account/region behavior;
- whether a future Tuya-local backend belongs in this adapter.
